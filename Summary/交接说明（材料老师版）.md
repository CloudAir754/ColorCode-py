## 1. 这套程序做什么

试样表面有一个 3×3 的彩色色块阵列。程序完成两件事：

1. 读出九个位置分别是什么颜色，据此识别试样编号和颜色变化阶段；
2. 测量色块的平均长宽比，据此给出拉伸比，并结合视频时间得到阶段转换时间和拉伸速度。

它不是“训练出来的神经网络”，也没有模型文件。它更像一套固定的实验判据：先找边界，再找三个绿色定位块，最后在九个格子的中央取色并按 HSV 阈值分类。因此，光照、拍摄角度、色块尺寸和阈值会直接影响结果。

### 一个生活类比

可以把它想成“用九宫格模板检查一盒彩色糖果”：

- 先把照片缩放成固定大小，相当于统一尺子的刻度；
- 再把色块边缘描出来，相当于找每颗糖果的包装轮廓；
- 用左上—中央—右下的三个绿色块摆正九宫格模板；
- 只看每格中央，避开反光和边缘阴影；
- 把测到的颜色和预先写好的颜色范围表比较；
- 同时测量色块“高/宽”的变化，估计材料拉伸。

## 2. 数据从手机到结果怎样流动

```text
Android 拍摄/选择视频
        │
        │ 分片上传 POST /upload
        ▼
Python Flask 服务端合并 MP4
        │
        │ OpenCV 逐帧读取
        ▼
每帧：缩放 → 增亮 → 灰度 → 模糊 → 找边缘 → 补边缘
        │
        ▼
筛选四边形 → 找 3 个绿色对角定位块 → 建立 3×3 网格
        │
        ├── 每格中央取 HSV → Red/Yellow/Green/Blue/Black
        └── 四边形长宽比 → 拉伸比
        │
        ▼
按颜色数量判断 RGB、RG、G 三个阶段及时间点
        │
        │ Android 每 2 秒查询 GET /check_status/任务号
        ▼
Android 弹窗按 record / measure 两种模板显示阶段时间或拉伸结果
```

网络接口共有三个：

| 地址 | 用途 |
|---|---|
| `GET /ping` | 手机检查电脑服务是否在线 |
| `POST /upload` | 手机分片上传视频 |
| `GET /check_status/<任务号>` | 手机轮询分析结果 |

### 单帧内部处理过程

1. **统一尺寸**：所有图片缩放为 225×400 像素，减少不同手机分辨率带来的差异。
2. **亮度增强**：将 HSV 中亮度高于阈值的区域按 Gamma 规则增强。
3. **灰度化**：颜色暂时去掉，只保留明暗，便于寻找边界。
4. **高斯模糊**：压制细小噪点。
5. **Canny 边缘检测**：把亮度变化明显的位置变成白色边线。
6. **闭运算**：连接断裂边线、填补小孔。
7. **轮廓筛选**：按面积和尺寸留下疑似色块的四边形。
8. **绿色定位**：寻找恰好三个绿色块，并按左上到右下排序。这三个块决定九宫格的行列范围。
9. **颜色识别**：在每个格子中央约 2/3 的区域取平均 HSV，判为红、黄、绿、蓝或黑。
10. **拉伸测量**：计算各有效四边形的 `高度/宽度` 平均值。程序字段名为 `stretch_ratio`。

### 视频阶段怎样判断

- 还有蓝色：第一阶段 `RGB`；
- 蓝色消失、仍有红色：第二阶段 `RG`；
- 蓝色和红色都消失：第三阶段 `G`；
- 单帧识别失败：该帧不作为有效阶段。

试样编号使用第一阶段的六个非绿色位置。红色记为 1，其他颜色记为 0，组成 6 位二进制数，再映射到 `5D code01`～`5D code64`。

## 3. 输出文件在哪里、怎么看

### 正常通过 Android 上传视频

服务端输出在：

```text
ColorCode-py\out\日期时间\
```

其中：

- `Ori_数字.jpg`：统一尺寸后的原始帧；
- `frame_数字.jpg`：左边为轮廓定位，右边为颜色取样和分类结果；
- `out\202505`：手机上传的临时分片和合并后视频。

服务启动时会执行临时文件清理逻辑。需要长期保留的实验结果应及时复制到别处，不要把 `out` 当作永久档案。

### 使用“识别调试工具”

结果默认放在：

```text
ColorCode-py\debug_out\文件名_日期时间\
```

检查整段视频时会得到：

- `逐帧识别总览\frame_000001.jpg` 等：每帧定位和取色结果；
- `逐帧识别结果.csv`：可直接用 Excel 打开；
- `逐帧识别结果.json`：完整机器可读结果；
- `视频信息.json`：分辨率、帧率、总帧数和是否旋转；
- `本次参数.json`：本次调试所用参数，便于复现实验。

检查单图或指定视频帧时，`处理步骤` 文件夹包含：

| 文件 | 应观察什么 |
|---|---|
| `00_输入原图.png` | 拍摄是否清晰、是否反光、九宫格是否完整 |
| `00_Standard_Size_Pic.png` | 缩放后是否仍清晰 |
| `01_Gamma_Func..png` | 增亮后色块是否过曝或仍太暗 |
| `02_Gray_Func..png` | 色块与背景是否有明暗反差 |
| `03_GaussianBlur_Func..png` | 噪点是否减少、边界是否仍保留 |
| `04_Canny_Edge_Func..png` | 每个色块是否形成连续边线 |
| `05_CLOSED_Func..png` | 断口是否被连接，邻近色块是否误粘连 |
| `06_Green_Diagonals_Detection.png` | 是否只标出左上、中央、右下三个绿色块 |
| `07_Color_Detect.png` | 九格中央取色框及 HSV/颜色判断是否正确 |
| `08_Debug_View.png` | 有效轮廓、外接四边形和编号是否合理 |

`识别结果.json` 中最重要的字段：

- `status = Success`：该帧完整通过所有判据；
- `block_count`：初筛得到的四边形数量。理想情况常为 9，但它只是诊断线索，不是单独的成功标准；
- `color_matrix`：3×3 颜色矩阵；
- `stretch_ratio`：拉伸比；
- `error_info`：失败发生在哪一环节。

## 4. 推荐的调参方法

### 原则：一次只改一个参数

准备三类有代表性的图片：正常、偏暗、偏亮/反光。每次只改一个参数，用同样图片重跑，并把 `本次参数.json`、步骤图和结果一起保存。不要只让某一张“碰巧成功”，应以整批图片稳定为准。

命令行示例（在 `ColorCode-py` 文件夹的 PowerShell 中运行）：

```powershell
python debug_recognition.py "样品图片.jpg" --gamma 0.6 --brightness 100 --open-folder
python debug_recognition.py "实验视频.mp4" --step 5 --open-folder
python debug_recognition.py "实验视频.mp4" --frame 120 --canny-low 40 --kernel 7 --open-folder
```

若已运行“首次安装环境”，可把命令中的 `python` 换为：

```powershell
.\.venv\Scripts\python.exe
```

### 常用参数和现象

| 参数/命令选项 | 默认值 | 什么时候改 | 调大后的主要效果 | 调小后的主要效果 | 看哪张步骤图 |
|---|---:|---|---|---|---|
| `HP_gamma` / `--gamma` | 0.7 | 图片偏暗或增强后过曝 | 接近 1，增强变弱 | 增强更强 | `01_Gamma` |
| `HPbrightness_threshold` / `--brightness` | 120 | 增强区域太多或太少 | 只有更亮像素被增强 | 更多像素被增强 | `01_Gamma` |
| `HPt1Canny` / `--canny-low` | 50 | 边线太少或噪声太多 | 弱边缘减少 | 弱边缘增多，同时噪声也可能增多 | `04_Canny` |
| `HPt2Canny` / `--canny-high` | 150 | 强边界仍不稳定 | 认定强边缘更严格 | 更多边缘会成为强边缘 | `04_Canny` |
| `HPsizeGaussian` / `--gaussian` | 9 | 图像噪点多 | 更平滑，也可能抹掉细边界 | 保留细节，也保留噪声 | `03_GaussianBlur`、`04_Canny` |
| `HPkernel` / `--kernel` | 9 | 边线断裂或色块粘连 | 更容易连接断线，也更容易把相邻区域粘住 | 少粘连，但断线可能补不上 | `05_CLOSED` |
| `min_contour_area` / `--min-area` | 200 | 小噪点被当成色块，或真实小色块被丢弃 | 去掉更多小轮廓 | 保留更多小轮廓和噪点 | `08_Debug_View` |
| `HP_Black_th` / `--black` | 0.15 | 暗色被错判 | 更多暗颜色判为黑 | 更少颜色判为黑 | `07_Color_Detect` |
| `center_factor` / `--center` | 0.667 | 边缘反光污染取色 | 取样区域更大 | 只看更靠中央区域 | `07_Color_Detect` |
| `HP_ts_radio` / `--stretch-tolerance` | 0.3 | 个别轮廓长宽比不同导致整帧失败 | 容忍差异更大 | 判定更严格 | `08_Debug_View` 和 JSON |

必须使用正奇数作为 `--gaussian`，例如 3、5、7、9；`--black` 范围是 0～1；`--center` 大于 0 且不超过 1。调试脚本会检查这些基本错误。

### 只在确有证据时改的参数

这些参数目前没有放入基础调试命令，可在 `ColorCodeDetector\ColorCodeDetector.py` 中修改：

| 参数 | 默认值 | 含义和注意事项 |
|---|---:|---|
| `target_size_x/y` | 225/400 | 全部尺寸阈值都依赖它，不建议单独改 |
| `min_screen_coef` | 15 | 最小允许宽高约为图像尺寸的 `1/15`；数值越大，允许的最小色块反而越小 |
| `max_screen_coef` | 3 | 最大允许宽高约为图像尺寸的 `1/3`；数值越大，允许的最大色块反而越小 |
| `HP_Color_rules` | 见源码 | HSV 色相边界。只有在拿到大量实测 HSV 后再改 |
| `border_size` | 50 | 只给标注图留文字空间，通常不影响识别 |

`HP_lightest_pencent`、`HP_lightest_Min_threshold`、`HP_lightest_Max_threshold` 目前只是保留字段，没有进入实际算法；修改它们不会改变结果。`VideoProcessor.stability_threshold` 目前也没有参与阶段判断，不要把它当作有效调参项。

### 颜色阈值怎样调

默认色相范围为：红 `0～50` 和 `283～360`，黄 `50～70`，绿 `70～150`，蓝 `150～283`。黑色优先按亮度 `V < 0.15` 判断。

建议先勾选 `07_Color_Detect.png` 上显示的 H、S、V，收集每类颜色至少几十张、覆盖不同光照的数值，再移动边界。不要根据一张图修改颜色范围；红色跨越 0°/360°，两段都要保留。

### 常见失败—处理对照

| 现象 | 先检查 | 优先尝试 |
|---|---|---|
| `block_count` 远大于 9 | Canny 噪点、背景纹理 | 提高 Canny 阈值、增大模糊、提高最小面积 |
| `block_count` 小于 9 | 边线断裂、过暗、过曝 | 调 Gamma/亮度、降低 Canny 阈值、适当增大闭运算核 |
| 找不到 3 个绿色定位块 | 绿色 HSV、反光、三块没入镜 | 改善拍摄；核对 `06` 和 `07`，最后才调色相边界 |
| 相邻色块被连成一块 | 闭运算过强 | 减小 `kernel` |
| 彩色块判为黑色 | 黑阈值过高或曝光不足 | 改善照明，或降低 `black` |
| 颜色对但位置错 | 拍摄倾斜、绿色定位错误 | 尽量正对试样，保证三个绿色块完整清晰 |
| 拉伸比报离散过大 | 某个轮廓识别畸形 | 先修轮廓；确认真实允许后再增大 `stretch-tolerance` |

## 5. 视频时间预设与两种显示模式

`FlaskServer\video_processor.py` 中：

```python
USE_STORED_TRANSITION_TIMES = True
TRANSITION_TIME_MAPPING_SCOPE = TIME_MAPPING_SCOPE_IMAGE
```

当前流程：

1. 某种 3×3 颜色矩阵第一次完整识别时，记录三个阶段的时长，Android 显示 **record** 模板：
   - `T0: 0s RGB`
   - `T1: ...s RG`（RGB→RG 的时长）
   - `T2: ...s G`（RG→G 的时长）
   - `ΔT1=T1；ΔT2=T2；`
2. 同一服务进程内再次识别同一矩阵时，复用第一次的时间，在当前视频对应时刻取拉伸比，Android 显示 **measure** 模板：
   - `Name`、`RGB α0`、`RG α1`、`G α2`
   - `ΔT1/ΔT2（known）`
   - `Speed: ... mm/min`
3. 这些时间只存在内存中，关闭或重启服务后清空。

可选配置：

- `USE_STORED_TRANSITION_TIMES = False`：每次都使用当前视频自己的阶段时间，不缓存；
- `TRANSITION_TIME_MAPPING_SCOPE = TIME_MAPPING_SCOPE_IMAGE`：每种颜色矩阵分别缓存，推荐；
- `TRANSITION_TIME_MAPPING_SCOPE = TIME_MAPPING_SCOPE_PROGRAM`：所有试样共用第一份时间预设，除非实验方案明确要求，否则不建议。

速度按 `(α2 - α0) / 100 × 材料长度 ÷ (ΔT1 + ΔT2) × 60` 计算，单位为 mm/min。材料长度在 `FlaskServer\experiment_config.py` 的 `PRESET_MATERIAL_LENGTH_MM` 修改，默认 50 mm。完整说明见 [双显示模式说明](双显示模式说明.md)。

### 让修改生效

1. 保存 `display_test_config.py`；
2. 关闭原来的服务窗口；
3. 重新双击 `启动服务.bat`；
4. Android 选择 **Remote Upload**，上传任意视频；
5. 点击上传成功弹窗中的 **Start video analysis**，查看结果弹窗；
6. 测试结束后务必改回 `DISPLAY_TEST_MODE = None` 并重启服务，否则真实视频也只会返回假数据。

两种模板的逐字样例、速度公式和字段说明见 [双显示模式说明](双显示模式说明.md)。

## 8. Android 文案在哪里改

### 常规按钮和固定文字

文件：

```text
ColorCode-Andrioid\app\src\main\res\values\strings.xml
```

常见项目：

- `app_name`：应用名称；
- `Btn_record`、`Btn_stop`、`Btn_config`、`Btn_select_video`：主界面按钮；
- `local_frames_mode`、`remote_upload_mode`：本地拆帧/远程上传；
- `NetworkDetect_*`：网络状态；
- `ProgressDialog*`：拆帧进度提示；
- `clean_*`：清理文件提示。

应用内说明文字在：

```text
app\src\main\res\values\readme_strings.xml
```

### 识别结果弹窗文字

文件：

```text
app\src\main\java\com\cloudair754\sendvideos\ResultDisplayFormatter.kt
```

重点搜索这些文字：

- `Image infomation`（按确认的模板保留原拼写）
- `Details`
- `T0` / `T1` / `T2`
- `Name`
- `RGB α0` / `RG α1` / `G α2`
- `ΔT1` / `ΔT2`
- `Speed`
- `Processing results`（弹窗标题，在 `VideoUploader.kt`）

上传成功、轮询超时、解析失败等 Toast 也有一部分直接写在 `VideoUploader.kt` 中。修改文案后必须重新构建并安装 APK；修改 Python 假数据只需重启 Python 服务。

不要随意修改 JSON 字段名，如 `mode`、`info`、`stages`、`stretch_percent`、`time_differences`、`speed`、`delta_t1`、`delta_t2`。这些是手机和服务端约定的数据接口，改一边会导致另一边无法解析。

## 9. 日常实验建议

- 手机尽量正对试样，固定距离、焦距和曝光；比反复调算法更可靠。
- 光源使用稳定、均匀的漫射光，避免频闪和镜面反射。
- 保证九个色块完整入镜，尤其是左上、中央、右下三个绿色定位块。
- 每次改参数记录日期、样品、光照、手机、参数 JSON 和成功率。
- 建立固定验证集，不要用参与调参的单张图片判断最终效果。
- Android 弹窗只是摘要；出现争议时以服务端逐帧图片、CSV 和原视频为准。

## 10. 故障排查清单

### 双击服务窗口立即关闭

先运行 `首次安装环境.bat`。若仍失败，从 PowerShell 进入 `ColorCode-py` 后运行：

```powershell
.\.venv\Scripts\python.exe runServer.py
```

窗口会保留具体报错。

### 手机一直显示连接失败

依次检查：服务窗口是否开启、IP 是否写对、是否带 `http://` 和 `:5000`、是否误加 `/upload`、手机电脑是否同网、Windows 防火墙是否允许、手机浏览器能否打开 `/ping`。

### 上传成功但一直没有结果

客户端默认每 2 秒查询一次，最多 30 次，约 1 分钟。长视频逐帧分析可能超过 1 分钟，此时客户端会提示超时，但服务端后台可能仍在处理。先看服务窗口和 `out` 是否继续生成图片；测试通信时可临时使用伪输出模式。

### 调试视频太慢或生成文件太多

默认检查每一帧。可用 `--step 5` 表示每 5 帧检查一帧：

```powershell
python debug_recognition.py "实验视频.mp4" --step 5 --open-folder
```

正式 Android 分析仍会处理每一帧；`--step` 只影响人工调试工具。

### 需要确认代码没有被改坏

在 `ColorCode-py` 中运行自动测试：

```powershell
python -m unittest discover -s tests -v
```

看到最后一行 `OK` 表示现有自动测试通过。它主要覆盖 Android 伪输出结构、两种弹窗文案、视频时间缓存和速度公式，不能替代真实图片/视频验证。
